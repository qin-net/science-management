# 005 P0.6：最小驾驶舱（工作区总览）

- 状态：已实现，验收证据见第 7 节（HOME-01、HOME-03 仍为进行中：只有计数与我的待办）
- 需求映射：`HOME-01`（科研进度总览，部分：只有计数，没有「进度百分比」）、`HOME-03`（智能任务面板，部分：只汇总「我的待办」，不含 AI 建议）。`HOME-06`、`HOME-07`、`HOME-10` 在本切片**不做**，见非目标
- 依赖：[001](./001-p0-workspace-paper-import.md)（成员、项目、文献）、[004](./004-p0-tasks.md)（任务与逾期口径）、事件表；决策 D-017，新增 D-019

## 1. 问题、目标、范围

**问题**：登录后首页只有项目名称列表。要知道「哪个项目有逾期任务、我手上有什么待办、最近谁动了什么」，得逐个点进项目。

**目标**：首页给出这个工作区的真实总览：每个项目的文献数、任务状态计数、逾期数、最近活动时间；跨项目的「我的待办」；最近动态。每个数字都来自库里的真实记录，口径写在页面上；没有数据时说没有，不画假图。

**范围内**

- 一个只读接口 `GET /workspaces/{id}/overview`
- 首页的总览区：汇总计数、我的待办、项目卡片上的计数、最近动态、口径说明
- 空工作区、空项目、全部完成时的空状态

**非目标**

| 不做 | 原因与去向 |
| --- | --- |
| 「进度百分比」「研究健康度」「风险/机会」（HOME-01 的评分部分、HOME-13） | 没有可以据此计算的定义，任何百分比都是编造。只展示计数 |
| AI 建议的下一步、日报（HOME-02、HOME-09、HOME-03 的 AI 部分） | 需要模型，见 D-017 |
| 阅读数量、研究方向、知识覆盖（HOME-06） | 系统里没有「读过」的记录，也没有方向分类；文献数只是导入数量，不等于阅读量 |
| 科研时间轴（HOME-07）、组会与投稿倒计时（HOME-10、HOME-11） | 时间轴需要里程碑；组会和投稿对象还不存在 |
| 图表、趋势、按时间的统计 | 目前没有足够的历史数据，也没有定义好的周期；先把计数做对 |
| 跨工作区汇总 | 工作区是权限边界（D-003），总览按当前选中的工作区 |

## 2. 用户场景与行为

### 2.1 权限

任何工作区成员（包括 viewer）可以看总览。非成员 404。总览只含该成员本来就能在项目页看到的内容，不新增可见范围。

### 2.2 内容与口径

| 项 | 口径 |
| --- | --- |
| 汇总：活跃项目数、归档项目数 | 按项目状态 |
| 汇总：文献数 | 工作区内所有项目的文献条数（含无 PDF 的，含归档项目） |
| 汇总：未完成任务数 | 活跃项目中状态为 `todo`、`doing`、`blocked` 的任务数 |
| 汇总：逾期任务数 | 活跃项目中按 spec 004 第 2.4 节算出的逾期任务数 |
| 项目：文献数 | 该项目的文献条数 |
| 项目：已解析文献数 | 当前版本存在当前解析结果的文献数（有解析成功的块可读） |
| 项目：任务计数 | 按状态的五个计数，加逾期数（含归档项目，便于查看；归档项目的任务不进入汇总和「我的待办」） |
| 项目：最近活动 | 该项目事件的最晚时间；没有事件为空 |
| 我的待办 | 活跃项目中，负责人是当前用户且状态为 `todo`、`doing`、`blocked` 的任务；逾期的在前，然后按期限从早到晚，没有期限的在最后，同组内按创建时间新的在前；最多 20 条，另给总数 |
| 最近动态 | 工作区内项目事件，最新的在前，最多 20 条；带项目名和操作者名 |

「我的待办」只含分给我的任务，不含未分配的。未分配的任务在项目页看板里。

动态沿用事件的约定：不含标题、正文、原因等文字，所以总览同样不显示这些文字，只显示「谁在哪个项目做了什么类型的操作」。

### 2.3 页面

- 总览区在项目列表上方：四个汇总数字、「我的待办」、「最近动态」；项目列表的每个项目下增加一行计数。
- 页面有一段折叠的「统计口径」，写明上表的定义。
- 空状态：没有项目时不显示总览区的数字块，只有原有的创建提示；「我的待办」为空时写「没有分给你的未完成任务」；没有动态时写「还没有动态」。
- 「我的待办」每条链接到所属项目，显示项目名、状态、期限、逾期标记。逾期标记只显示接口返回的 `overdue`。
- 计数为 0 就显示 0，不隐藏。

### 3.1 `GET /api/v1/workspaces/{id}/overview`

```json
{"today": "2026-10-31",
 "totals": {"active_projects": 2, "archived_projects": 1, "papers": 7,
            "open_tasks": 5, "overdue_tasks": 1},
 "projects": [{"id": "…", "name": "…", "status": "active", "paper_count": 4,
               "parsed_paper_count": 3,
               "tasks": {"todo": 2, "doing": 1, "blocked": 0, "done": 3, "cancelled": 0, "overdue": 1},
               "last_activity_at": "…"}],
 "my_tasks": {"total": 3, "items": [{"id": "…", "title": "…", "status": "doing",
              "priority": "high", "due_date": "2026-10-30", "overdue": true,
              "project_id": "…", "project_name": "…"}]},
 "recent_events": [{"id": "…", "event_type": "task.created", "project_id": "…",
                    "project_name": "…", "actor_name": "…", "created_at": "…"}]}
```

`projects` 按创建时间倒序，与现有项目列表一致。`today` 是服务端用来判断逾期的 UTC 日期，页面据此说明口径。

任务标题出现在「我的待办」里，这是任务本身的内容，不是事件；该用户本来就能在项目页看到。

## 4. 验收标准

后端用例同样用真实 PostgreSQL，不用 mock。

- P1 Given 非成员，Then 404；viewer、member 都可以读，且内容相同（除「我的待办」按调用者）。
- P2 Given 两个项目（一个归档）、若干文献和任务，Then 汇总、项目计数与手工算的一致；归档项目的任务不进入汇总和「我的待办」，但项目卡片上有计数。
- P3 Given 一个 PDF 文献已解析、一个仅元数据、一个解析失败，Then `parsed_paper_count` 只计第一个，`paper_count` 计三个。
- P4 Given 任务分给不同的人，Then 「我的待办」只含分给调用者且未完成的；完成、取消的和未分配的不在其中；逾期的排在前，再按期限，无期限的最后；超过 20 条时 `total` 是真实总数、`items` 为 20 条。
- P5 Given 其他工作区的项目、任务和事件，Then 一概不出现在总览里。
- P6 Given 事件，Then `recent_events` 最新的在前、最多 20 条，只含工作区项目的事件，不含任务标题、笔记正文等文字。
- P7 Given 空工作区（没有项目），Then 所有计数为 0，列表为空，不报错。
- P8 Given 项目没有任何事件，Then `last_activity_at` 为 null（不是错误，不是当前时间）。
- P9 Given 调用者已不是负责人所在工作区的成员或任务被移走，Then 随之更新（总览是读时计算，不缓存）。

**界面（真实浏览器）**

- N1 Given 有项目和任务，Then 首页显示与库里一致的汇总数字和项目计数，刷新后不变。
- N2 Given 分给我的逾期任务，Then 「我的待办」里该任务排第一并带「已逾期」；点击进入所属项目。
- N3 Given 新工作区，Then 显示空状态文案，没有 NaN、undefined 或空白块。
- N4 Given viewer，Then 能看到总览，「我的待办」为空并说明原因（没有分给你的任务）。
- N5 Given 在项目里改了任务状态，When 回首页，Then 数字随之变化；「统计口径」可展开并包含「逾期」「已解析」的定义。

## 5. 技术决策与风险

决策见 [DECISIONS.md](./DECISIONS.md) 的 D-019。

| 风险 | 处理 |
| --- | --- |
| 数字来自页面自己的算法，各处口径不一致 | 全部由服务端算，逾期复用任务接口的同一个函数；页面只显示 |
| 总览泄露用户本来看不到的内容 | 只查调用者所在工作区；事件不含文字；用例 P5、P6 |
| 一个工作区项目很多时查询变慢 | 用分组聚合，不逐项目查询；本切片不分页，项目数以数百为限，超过时需要重新设计，写入已知限制 |
| 编造的指标让人误以为有「进度」 | 非目标明确不做百分比和评分，页面只展示计数 |

**未验证的假设**：工作区内项目数不超过数百；没有做性能测量。

| N1 至 N5 | `web/e2e/overview.spec.ts` 的 5 个用例，名称以 N1…N5 开头 |

**可失败性检查**：逐个改坏 `overview.py`，`test_overview.py` 应失败。15 处改动中 14 处立刻被抓住：归档项目计入未完成数、归档项目计入逾期数、「我的待办」不按负责人、含归档项目、含已完成任务、无期限排在前面、不限 20 条、`total` 不真实、文献数跨工作区、动态最旧在前、动态不限数量、「已解析」数含所有文献、无事件时给出当前时间、项目最旧在前。

第 15 处「逾期不排在前」没有被抓住。原因是它不是独立的规则：「我的待办」里的任务都是未完成的，按期限从早到晚排序时，逾期的（期限早于今天）必然在不逾期的前面。已删去多余的排序项，改为只按期限排序，并在代码里写明。改完后再次检查：把无期限任务改排最前（`nulls_first`）仍被抓住；单纯去掉 `nulls_last` 不会失败，因为 PostgreSQL 升序时 NULL 本来就排最后，这个写法只是把依赖的行为写明，不算独立的防线。

**过程中发现并修复的缺陷**：无。

### 7.3 未验证与已知限制

- 「今天」按服务器 UTC 日期算，与任务看板一致（spec 004 2.4）。
- 没有进度百分比，文献数只是导入条数；见 D-019。
- 项目数没有分页，也没有做性能测量；超过数百个项目时需要重新设计。
- 总览是读时计算，每次打开首页都会重算，没有缓存。
- N4 里 viewer 只有一个工作区，没有测多工作区切换时总览随之切换。
- 总览只显示当前选中的工作区，没有跨工作区汇总。
- 最近动态只含带项目的事件，没有分页或「查看更多」。
- e2e 只在 Chromium 上跑过。
